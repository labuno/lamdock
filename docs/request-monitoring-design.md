# 请求监控的数据口径与采集边界

状态：第一版网关监控已实现。用户优先要求准确性：不能保证的数据宁愿不显示。官方直连采集尚未接入。

## 当前产品决定

基于本地会话日志的 Usage 模块已取消，包括 token 汇总、估算费用、活动热力图、缓存汇总、价格表、后台索引和 PAT 归属时间线。
保留已有官方额度查询、会话管理、帐号切换与 Gateway 请求观测。历史数据库与日志不删除，也不再参与这些操作。

热力图、缓存统计与首 token 记录仅可在采集与口径已验证后重新提供，不能沿用已下线汇总或响应头延迟作为替代。

## 可用来源与限制

| 来源               | 可说明的事实                             | 覆盖限制                                                        |
| ------------------ | ---------------------------------------- | --------------------------------------------------------------- |
| Gateway 请求元数据 | 经过网关的请求状态、耗时、首内容增量和可选上游 usage | 不覆盖官方 Codex 或原生 Responses 直连；缺失字段为未知 |
| 官方额度／费用接口 | 接口声明范围内的额度、费用或重置信息     | 不等同本地 token 总量；可能按时间窗口聚合                       |

Gateway 记录写入 Provider Hub 下的 `gateway-requests.jsonl`。版本2增加时间、模型、缓存、独立观测 ID 和流结束状态；帐号/服务商只保存散列，通过当前 Provider 绑定解析名称，删除后显示未知。
旧记录中的 `ttftMs` 来自响应头，全部排除。版本2的 `headersMs` 单独保存响应头耗时；`ttftMs` 是网关开始处理请求至首个非空文本、推理、拒绝或工具输入增量的观测时间，包含排队/重试。页面使用 First content，避免将它误解为模型内部生成时间。非流式请求不展示该时间。

## 当前页面与查询

- 底部 Monitor 入口；按本地日期、服务商、模型和结果筛选，默认每10秒刷新。仅展示已经结束的 Responses 请求观测，不显示在途进度；健康检查、模型列表、鉴权失败和读取请求体前失败不在此列表。
- 热图为已记录请求的开始日期；空格表示没有记录，不能据此推断未使用或采集连续。
- 缓存命中率为样本中 cached/input 的加权比例，仅纳入明确返回输入、输出和缓存字段且没有重试的请求；显示样本数。明确0与缺失分开，分母0时不显示比例。
- 首内容卡显示实际测量样本的中位数及数量。逐请求显示上游明确提供的输入/输出/缓存/推理，不推算费用和帐号消费总量。
- 独立 `recordId` 标识一次观测；重读同条记录按该 ID 去重，客户端复用 `requestId` 不会合并不同请求。重试行用量标记为末次尝试，不能代表全部尝试的消费。
- `query_request_monitor` 从最近8 MiB读取最多5000条新版请求；截断、损坏行、旧记录和写入中的尾行均有说明。读取失败明确报错，刷新失败保留上次成功结果并提示。
- 需要运行更新后的网关才会产生新版记录，不从历史会话日志补算。原始响应字节不变；流结束、失败或客户端取消时各记录一次，不新增正文或凭证存储。
- 未观察到可识别的结束事件时标为 `unverified`，不推断成功或网络中断；单帧超过256 KiB时停止解析指标，转发不受影响，未取得的字段保持未知。

## 实施前提

- 现有 Rust、网关和测试框架足以实现第一版网关监控，不需要新增远程服务器或额外监控服务帐号。
- 官方 Codex 提供默认关闭的 OpenTelemetry 导出，包含 API 请求、SSE／WebSocket 事件；可评估让 LamDock 在本机接收。接入时需要启用相应用户／帐号配置，并处理既有遥测配置，当前尚未修改。
- 本机 CLI 为 `codex-cli 0.164.0`。CLI、桌面应用及不同帐号使用的运行时需要分别验证，不能根据 CLI 版本推断所有客户端的采集能力。
- 先用受控请求核验事件能否关联到具体请求／重试，是否包含首个模型内容的准确时刻。官方文档列出的流事件和处理耗时不自动等于可用的首 token 指标；缺少证据时不展示。
- OTel 会批量导出，查询和时间差应使用事件本身的时间或明确的测量值，不能把接收器收到批次的时间当成请求或首 token 时间。
- 上游必须明确返回缓存 usage，才能纳入缓存统计；未返回时保持未知。最后用本机已配置的真实帐号验证，不要求导出密钥明文。

依据：[官方 OpenAI 文档：Monitoring and telemetry](https://learn.chatgpt.com/docs/agent-approvals-security#monitoring-and-telemetry)。

## 后续监控的必要合同

- 逐请求展示来源、覆盖范围、Agent、帐号、服务商、模型、状态与直接观测到的指标。
- Token 分项仅使用该请求上游明确返回的 usage；缺失为未知，不填 0。缓存属于输入、推理通常属于输出，不重复相加。
- 不展示无法核验的帐号总消费或按价格表推算的实际扣费。
- 首 token 必须采集真实模型内容事件；响应头、心跳和元数据不计入首 token。
- 热力图必须说明是请求发生时间还是已完成请求时间；无采集覆盖的时段不能标为零消费。
- 缓存统计仅包含已取得完整 usage 且能可靠去重的请求，并明确其覆盖范围。
- 未建立可靠请求 ID 关联时，不把本地记录和网关记录合并求和。
- 错误、取消、重试与缺失 usage 保留原有事实，不能根据状态猜测消费为零。
- 常规监控只持久化必要元数据，不新增 prompt、响应正文或认证头存储。
- 官方直连若也需要实时监控，必须先验证可用的采集边界；当前未修改认证、全局代理或直连路由。

## 验证场景

- 合成上游精确控制 usage、缓存分项、请求 ID 与时间，核验展示及去重。
- 分开发送响应头、心跳、推理和文本，验证首 token 测量边界。
- 验证流式结束、失败、取消和缺失数据时没有伪造零值。
- 验证官方额度与请求指标分开显示，未采集流量不会被计入或宣称已覆盖。

自动化验证对应 [网关采集测试](../apps/desktop/src-tauri/tests/provider_gateway_monitor.rs)、[查询测试](../apps/desktop/src-tauri/tests/request_monitor.rs) 和 [页面测试](../apps/desktop/src/routes/monitor.test.tsx)。已完成的任务流水已清理，现行实现与数据合同保留。本机受控上游已经覆盖协议适配、实际 HTTP 网关、元数据落盘及查询；未使用真实付费 API 请求作为验证依据。

## 第一版实施单元

本轮实现经过现有网关的请求监控。官方直连 OTel 接入仍需单独验证事件契约，第一版在页面明确显示未接入，不修改用户遥测配置。

- `capture`：补齐版本化的逐请求元数据、上游 usage、缓存及首内容增量计时；保留流终结和取消事实。
- `query`：读取已记录请求，排除旧计时、按请求 ID 去重，保留数据缺失与日志错误信息。
- `ui`：展示网关覆盖范围、活动热图、缓存样本、首内容延迟和请求列表；提供筛选、刷新及未知状态。
